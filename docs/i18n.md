# Internationalization

The application uses `next-intl` with the locales configured in `src/i18n/routing.ts`.

Current locales:

- `en` - default locale;
- `cs` - Czech locale;
- `uk` - Ukrainian locale (shown as "UA" in the language switcher, see `LOCALE_LABELS`).

Translations live in:

```text
messages/en.json
messages/cs.json
messages/uk.json
```

## Rules

- Add user-visible text to translation files instead of hardcoding it in JSX.
- Add the same key to every supported locale file in the same change.
- Keep the JSON key structure synchronized across locales.
- Preserve existing namespaces and interpolation parameters.
- Use server translation helpers in Server Components and the appropriate client hook in Client Components.
- When adding a locale, update routing, messages, and the relevant documentation together.

Keep technical error details in logs and expose localized, user-safe messages in the UI.

## Legal Documents

The privacy policy and terms of use live in `messages/legal/<locale>.json`, not in the main message files: `NextIntlClientProvider` sends the main files to the browser on every page, and the legal texts are long. Only Server Components read them, through `getLegalContent` in `src/features/legal/content.ts`. The Czech text is the binding version; the English and Ukrainian ones are translations and must say the same thing. `{name}` and `{email}` are filled from `LEGAL_OPERATOR` in `src/shared/constants/legal.ts`. When you change either file, update `LEGAL_EFFECTIVE_DATE` in the same file.

## Formatting

Dates and prices go through `formatDate` and `formatCzk` (`src/shared/helpers/`), which map an app locale to an Intl tag with `toIntlLocale` and `INTL_LOCALES` (`src/shared/constants/locales.ts`). Adding a locale fails type checking until it has an entry there, in `OG_LOCALES`, the legal content, and the breed search.
